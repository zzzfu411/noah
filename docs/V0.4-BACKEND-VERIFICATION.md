# Noah v0.4 后端实施与关键自检

日期：2026-10-02。范围：N14、N20、N21，以及动态成员和可选新增输入预算。本文记录已执行的局部检查；全量整合、桌面视觉、正式发布和真实模型验证以主 Spec 的最终记录为准。

按本轮要求，每阶段只执行能够判断核心行为的少量检查。所有新增运行场景都使用隔离数据及模拟 harness；没有调用付费模型，没有向用户已有讨论发消息。

## 1 讨论、成员和资料生命周期

实现位于 `src/store.ts`、`src/server.ts`、`src/queries.ts`。

- 数据版本升至 5。已有非空旧数据库升级前执行一致性 `VACUUM INTO` 备份，名称唯一；旧暂停状态、运行额度和消息 ID 保留。
- 归档阻止新派发及新消息，历史仍可检索和导出。恢复后的讨论为暂停状态，需要 owner 明确继续。已经开始的执行可以完成记账；后续错误不能把归档状态改成暂停。
- 新成员获得独立且不可复用的身份。可选择被动补送已有公开历史；补送不会启动模型。成员退出保留历史，取消尚未开始的投递，拒绝原成员的新工具调用，不声称结束外部原进程。
- `shareHistory` 控制自动补送，而非公开历史的读取权限。成员加入后仍可通过工具主动读取同讨论公开记录。
- 资料更新产生新 ID、revision、hash 和 previous_id。旧 ID/hash 仍能读取原快照；基于过期版本提交时要求重新载入。

关键检查：`tests/maturity-lifecycle.test.ts` 中归档恢复、成员/资料、正在运行时退出三条通过。磁盘备份检查使用保留旧消息与限额、版本号标记为 v4 的隔离 fixture；旧结构迁移的既有测试保留，最终整合时统一执行。

## 2 结构化提议及 owner 审阅

实现独立 `outcomes`、`outcome_revisions`、`outcome_decisions` 账本；提议种类为结论、异议、待决定问题。

- 每条提议需要 1–50 条同讨论公开消息作为依据；不能引用其他讨论消息。
- 作者身份来自工具凭证或 owner API。只有原作者能修订自己的提议；修订生成新版本，旧版本和旧确认仍保留。
- owner 确认或重新打开具体版本；确认不代表全体共识，也不改变讨论的运行状态。
- JSON 公共导出附所有提议版本、决定、成员加入/退出信息及资料版本，不增加私有运行输出或原生凭证。
- Agent 使用 `noah_propose_outcome`、`noah_revise_outcome`、`noah_read_outcomes`。提议对象通过 UI 与读取工具可见；当前不会仅因提议变化自动生成公开消息或启动其他 Agent。

关键检查：有依据的提议、少数意见保留、不可覆盖他人立场、修订后重新审阅、过期确认拒绝、历史导出组合为一条测试，已通过。

## 3 可选新增输入字节预算

默认 `context_budget_bytes=null`，继续自主讨论，不增加默认总次数或时长限制。

`Store.reserveContextBytes(conversationId, chargeKey, bytes)` 使用持久 `context_charges` 账本。相同 key 与相同字节数重试不会重复预留；预留可以独立提交，或与派发授权处于同一事务。

- managed 输入按实际提交字符串的 UTF-8 字节计量。预算不足时，在 `adapter.prompt` 之前暂停，撤回尚未提交的 run 与 used_runs，完整消息继续留在队列。
- pi 原会话正文 envelope 和短唤醒分别预留。同一代次、同一投递重取 inbox 不重复计入。正文已观察到之后，短唤醒预算不足也不能调用 `triggerTurn`。
- 预算预留与已观察到正文、已提交推理指标分开。预留不是供应商 token、现有原生上下文或账单费用；故障后的保守预留可能尚未得到实际观察回执。

关键检查：managed 预算/完整性/幂等一条通过；pi 重复 inbox、预算不足禁止唤醒、正文保留、解除预算后继续的一条通过。

## 4 调度和状态读取

- managed 队列按讨论轮转选择派发，保留最多两个受管运行并发与每成员的执行锁。该并发策略不是讨论总次数限制。
- `/api/state?compact=1` 返回最近 200 条消息、相应回执及需要关注的执行状态；最近 100 次运行只含元数据。全历史计量使用 `runMetrics`、`deliveryCounts` 汇总。
- 私有运行输出通过 `/api/conversations/:id/runs` 显式分页读取，可按成员筛选。旧消息的回执可按 `messageIds` 定位，不以轻量快照遗漏冒充未投递。
- SSE 只读取最新事件 ID 进行失效通知，不为每次通知序列化全部状态。
- 轻量快照的提议版本历史另由讨论 outcomes 接口读取。它不是完整数据库备份。

三条关键测试均通过：

| 场景 | 观察结果 | 边界 |
| --- | --- | --- |
| 20 场讨论，每场 3 位模拟成员 | 60 次启动；前 20 次已覆盖全部讨论；一次运行等待 P50 167.3 ms、P95 315.0 ms | 本机模拟，不含模型供应商及网络延迟 |
| 运行与回执分页 | 顺序、讨论范围、完整持久输出及按旧消息定位回执正确 | 使用稳定本地 rowid 游标；不是跨数据库迁移游标 |
| 240 次运行，每次 16.8 KB 私有输出 | 常规快照 4,499,809 B，轻量快照 135,116 B；全历史计量仍为 240 次 | 固定样本，不表示所有实际工作负载都有同等降幅 |

状态仍会包含所有讨论/成员和当前提议；超大项目的汇总 SQL 成本、外部 binding 间公平性不是本次上述模拟的结论。

## 5 HTTP 关键路径

`tests/maturity-http.test.ts` 一条完整本机 HTTP 流程已通过：创建与暂停 → 公开消息 → 补送新成员 → 回执定位 → 资料修订与旧版读取 → 提议确认及修订 → 成员退出 → 归档 → 禁止直接恢复执行 → JSON 导出 → 恢复为暂停。模型启动数为 0。

测试使用临时数据目录、随机 loopback 端口和模拟 Engine。默认沙箱首次拒绝本机端口监听；通过仅此测试所需的提升权限运行后通过，不是产品接口失败。
